# Decisions

Newest last. Each entry: context → decision → consequences. Superseded decisions stay and are marked.

## D-001 — Python tooling (2026-10-10)

- **Decision:** Python **3.12** (pinned in `.python-version`, `requires-python = ">=3.12,<3.13"`), managed with
  **uv 0.13**; hatchling build backend; package `f1ar` at `backend/src/f1ar` (the plan's layout), installed
  editable. Dev tools are pytest, ruff and mypy (strict).
- **Why:** 3.12 is mature and widely supported by the ML stack (torch, SB3, FastF1). uv gives a lockfile and
  fast, reproducible installs on Windows without Docker.
- **Consequence:** If TUM race-simulation needs Python 3.8, it gets an isolated sandbox env and never enters
  this env (see D-003).

## D-002 — Early visibility before M3 (2026-10-10)

- **Context:** The plan delivers the first real UI at M3 (~6–10 weeks in). The owner wants to see some
  progress and "a bit of the world" before then.
- **Decision:** Add two lightweight, **read-only** views. Neither changes the architecture:
  1. **Terminal timing tower** in `scripts/demo_headless.py`: live tick/lap/position/tyre table while the
     headless world runs.
  2. **M0.5 Debug Viewer**: a single build-free HTML page served by the backend. It draws the Monza
     outline (FastF1 position data or the TUM racetrack-database centerline) and car dots from the canonical
     state, by polling. Pause/step buttons only *send commands*; the page never simulates.
- **Guardrails:** The backend stays authoritative and the viewer computes no race state (plan §1.3, §21.6).
  The viewer is clearly labelled "debug". It is replaced by the React/Vite UI at M3, not grown into it.

## D-003 — Simulator fallback pre-approved (2026-10-10)

- **Decision:** The TUM race-simulation feasibility check (M0) is time-boxed. If it can't be wrapped in a
  bounded `step()` + `get_state/set_state` adapter on modern Python, we go straight to **option C**: our own
  lightweight event/segment race engine calibrated on FastF1 data (no physics). The owner approved this
  in advance.

## D-005 — Canonical state encoding (2026-10-10)

- **Decision:** World state is hashed via canonical JSON (sorted keys, fixed separators, UTF-8, NaN/Inf
  rejected, JSON-native types only) → `sha256:<hex>`. See `f1ar/persistence/snapshot_codec.py`. Line
  endings are normalised to LF via `.gitattributes`, so tracked fixtures hash the same everywhere.

## D-006 — Race-specific rosters from Jolpica (2026-10-10)

- **Decision:** Identity and entry data (name, number, team, grid) live in one roster file **per event**,
  `configs/rosters/<event_id>.json`. It is generated by `scripts/build_roster.py` from Jolpica-F1
  `results.json` and labelled `historical_verified` with the source URL and retrieval time. Finishing
  results are deliberately excluded from the roster.
- **Deviation from plan:** The plan names a `season_roster_2024.json`. We use per-event files instead,
  because the plan itself requires per-race rosters (§5.2): seats changed mid-2024, and Colapinto
  debuted at Monza.
- **IDs:** `driver_id = <given>_<family>_<season>` (ASCII slug, e.g. `nico_hulkenberg_2024`),
  `person_id` without the season, `team_id = <jolpica constructorId>_<season>`. Event id `2024_italian_gp`.

## D-007 — Profiles = template + overrides, pinned by hash (2026-10-10)

- **Decision:** A profile seed names a template (`generic_balanced|veteran|rookie`) plus explicit
  overrides per driver. The resolved profile records `base_template` and `overridden_fields`, so the
  chosen and inherited values stay distinguishable. A persona's `numeric_values_source_type` is
  restricted by type to editorial / estimated / learned, so it can never claim `historical_verified`.
- **Pinning:** `ProfileSet.manifest_hash` (canonical sha256 over all resolved profiles) is what worlds
  will pin (`profile_manifest_hash`, plan §4.4). `profile_revision` is the human label.
- **Policy input:** `DriverProfile.features()` returns the 14-value vector under the stable names
  `PROFILE_FEATURE_NAMES` (`profile.<field>`). The observation schema in step 3 embeds this block.

## D-008 — Immutable world state, pure bounded step (2026-10-11)

- **Decision:** `WorldState` is a frozen Pydantic model holding *everything* that affects the future:
  the race setup (track, lap-model coefficients, embedded resolved driver profiles), car states, the
  tick, and the RNG spec. `lightweight_engine.step(state) -> StepResult(state, events)` is pure and
  advances exactly one tick (default 0.5 sim-seconds). `sim_clock_s` is derived as
  `tick * tick_seconds`, never accumulated.
- **Why:** Fork = keep the old object; save = serialize one object; replay = re-run pure steps. A
  bounded tick gives the ≤1-tick pause guarantee of plan §4.2.
- **Cost:** Copying a Pydantic object per tick costs about 9 µs per tick for 2 cars (a full 53-lap race
  takes about 0.08 s). If RL training later needs more throughput, add a fast internal representation
  behind the same API.

## D-009 — Keyed random numbers instead of a stateful RNG (2026-10-11)

- **Decision:** Every random draw is `f(seed, key...)`, e.g. `normal(seed, "lap_noise", driver_id,
  lap)`, built on SHA-256 (`f1ar/simulation/rng_streams.py`, scheme `sha256-keyed-v1`). The world saves
  only `{scheme, seed}`.
- **Why:** There's no generator state to serialize, so save/load can't drift. It also gives plan
  §4.5's common random numbers for free: forks and added cars don't shift anyone else's draws (tested).
- **Limit:** Normals use `math.log/cos`. Bitwise equality is guaranteed on one machine/libm (plan's
  "deterministic CPU mode"), not across platforms.

## D-010 — Minimal lap model is a placeholder (2026-10-11)

- **Decision:** `lap = base + skill_gap·(1−pace) + compound + degradation(age, compound,
  tire_management, pace_mode) + fuel·laps_remaining + pace_mode + N(0, sd(consistency))`. The
  coefficients are synthetic (`editorial_assumption`) and chosen only to look plausible for Monza
  (~84 s laps, ~74 min race). `risk_appetite` deliberately does **not** enter the transition model; it is a
  strategy preference. The model is replaced or calibrated from FastF1 in M1/M4.

## D-011 — WorldRunner: commands at tick boundaries, pacing kept separate (2026-10-11)

- **Decision:** `f1ar/simulation/world_runner.py` owns one live world. Commands (`START`, `PAUSE`,
  `RESUME`, `SET_SPEED` ∈ {1,2,5,10,25}, `STEP` N ticks while paused) are queued and applied **only
  between ticks**. Each returns a `CommandAck` with the exact `applied_tick`. Invalid commands are
  rejected with a reason, never raised, and every command is recorded in a command log.
- **Pacing:** Real time only determines *how many* ticks are due:
  `due = anchor_tick + floor((now − anchor_wall)·speed / tick_seconds)`. Start, resume and speed
  changes re-anchor, so paused time is never caught up. Catch-up per pump is capped; if the runner
  can't keep up, the sim slows down rather than jumping ahead. Tested: an arbitrary mix of
  pauses and speeds ends in the same canonical state as plain stepping.
- **Idempotency:** A repeated `idempotency_key` returns the original ack (`duplicate=True`) and is not
  re-applied (plan §4.7 test 9).
- **Threading:** `pump(now)` is the deterministic core, testable with a fake clock.
  `start_background()` runs it on one thread with `time.monotonic`. States are immutable, so readers
  get a consistent snapshot without copying. Measured pause ack in tests: well under the 250 ms
  target (plan §4.2).

## D-012 — SQLite snapshot store: full state blob + checksum, one transaction (2026-10-11)

- **Decision:** `f1ar/persistence/sqlite_store.py`. One SQLite file (WAL, `foreign_keys=ON`,
  `synchronous=FULL`) with `worlds`, `timelines`, `snapshots` and `store_meta(schema_version)`. A
  snapshot row stores the **canonical JSON of the whole `WorldState`** plus its SHA-256, inserted in a
  single `BEGIN IMMEDIATE … COMMIT`. This is plan §4.6's "state blob + manifest in one transaction"
  option, chosen over temp-file + rename because it is atomic by construction on Windows too.
- **Load verifies everything** before returning a state: schema, codec and engine version must match
  the running build exactly (no silent migration or engine swap), the stored type must be a BLOB, the
  checksum must match, and the decoded state must re-encode to the same hash. `latest_valid(world)`
  finds the newest snapshot that passes, for recovery (plan §4.7 test 7).
- **Snapshots are immutable** (insert-only). The store opens from any thread behind one lock, because
  the runner thread saves while others read.
- **Runner:** `CommandType.SAVE` saves at a tick boundary. The ack carries `snapshot_id` and is sent
  only after commit. Any store error turns into `accepted=False, reason="save failed: …"`, and the
  world keeps running (plan US-09).
- **Not yet:** event log and command log tables, autosave, timeline/fork records beyond the main
  timeline (step 6 / M2).

## D-013 — Forks, timelines and the first driver action (2026-10-12)

- **Fork = copy under a new timeline id** (`f1ar/simulation/timeline.py::fork_world`). It keeps the
  `world_id`, sets `parent_timeline_id`, and a RUNNING source forks as PAUSED. Because `WorldState` is
  immutable and complete, the source can't be affected (tested via snapshot hash and by replaying the
  source to the flag).
- **Seed modes** (plan §4.5, §13.3): `COMMON_EXOGENOUS_RANDOMNESS` (default) keeps the parent seed, so
  the branch sees identical (driver, lap) noise and differences come from the decision.
  `INDEPENDENT` derives a new seed from (parent seed, timeline id), so it is reproducible.
- **Store** (`SnapshotStore.fork`, `list_timelines`, `delete_snapshot`): a branch's first snapshot is
  a full copy, and `timelines.fork_snapshot_id` records provenance as plain text (not a foreign key),
  so deleting the source snapshot breaks neither the branch nor its recorded history (plan §4.7
  test 6). A branch whose parent was only in memory still records the parent, labelled `(unsaved)`.
- **Store schema v2** adds `timelines.label` and `fork_snapshot_id`. `STORE_MIGRATIONS` upgrades v1
  files in place, one transaction per version (the first real migration).
- **First driver action: `SetPaceMode`** (`engine.apply_action`, runner `SET_PACE_MODE`). It's pure,
  emits `PACE_MODE_CHANGED`, and takes effect from the driver's next lap (the lap in progress was
  sampled at its start). Re-requesting the same mode is an accepted no-op. Pit stops come in M2, so
  for now pace mode is the decision forks can differ by.

## D-014 — Tyre wear is path-dependent state; engine v0.2.0, world schema v2 (2026-10-12)

- **Bug found by the fork demo:** engine v0.1.0 computed degradation as `tyre_age × rate ×
  pace_mode_multiplier`, so changing mode retroactively rescaled the whole stint's wear. Pushing on
  43-lap-old tyres instantly added about 0.7 s/lap and made a late push *slower*; conserving "healed"
  tyres.
- **Fix:** `CarState.tyre_wear_s` accumulates `compound_deg × wear_factor(tire_management) ×
  mode_multiplier` per completed lap, at the mode that lap was driven in (`CarState.lap_pace_mode`,
  locked at lap start; `pace_mode` is the intent for the next lap). Supersedes the degradation term
  of D-010. `tyre_wear_s` is hidden from observations (inferred, not measured).
- **Versioning:** `ENGINE_VERSION = lightweight_engine_v0.2.0`, `WORLD_SCHEMA_VERSION = 2`. Saves from
  v0.1.0 are refused with `UnsupportedSnapshotError` (shown as INVALID by `inspect_save.py`) instead
  of being silently re-simulated under different physics. The gate demo's reference hash changed
  from `071ad86…` to `8ec919a…`.

## D-015 — FastF1 data pipeline: normalised Parquet + manifest + generated quality report (2026-10-12)

- **Pipeline** (`scripts/fetch_monza_2024.py`, plan §6.4): FastF1 `load(laps, telemetry, weather,
  messages)` with its on-disk cache → pure normalisers (`f1ar/data/fastf1_adapter.py`) → Parquet in
  `data/processed/<event>/` → manifest `data/manifests/<event>_fastf1.yaml` (SHA-256, rows, columns,
  `source_type` per file, units, missingness) → report `docs/data/<event>_quality.md`.
  `--verify` re-hashes files against the manifest.
- **Conventions:** snake_case, unit suffixes (`_s`, `_m`, `_c`, `_kph`), session-time seconds as
  float, positions converted from FastF1's 1/10 m to metres, nullable `Int64`/`boolean`/`string`
  dtypes so missing stays missing. The track outline (one green lap of the winner) is labelled
  `estimated_from_data`; everything else `historical_verified`.
- **Quality checks** are typed PASS/WARN/FAIL. FAIL = the data contradicts itself or our roster.
  WARN = a real race feature the simulator must handle (lapped cars, DNF, deleted laps), or a gap.
  The script exits non-zero on FAIL.
- **Independent cross-check:** FastF1 vs Jolpica on numbers, codes, grid, team pairing, finishing
  position and laps. All agree for 2024 Monza.
- **FastF1 swallows load failures** (logs "Failed to load ...", returns a partial session).
  `load_race_session` verifies laps and results exist and raises `DataSourceError` otherwise.
  Found by running with `-W error`: a NumPy 2.5 deprecation inside FastF1/pandas made it silently
  return no laps. The lockfile pins working versions; upgrades must re-run `pytest -m network`.
- **Tests:** offline tests use synthetic FastF1-shaped frames. The real fetch is an opt-in
  `network` test (`uv run pytest -m network`), excluded by default.

## D-016 — Simulator: our engine (option C); TUM simulators no-go (2026-10-12)

- **Decision:** Keep and grow `lightweight_engine`. Don't wrap or vendor TUM race-simulation or the
  TUM time-discrete simulator. Full evidence: `docs/SIMULATOR_DECISION.md`; reproducible probe:
  `scripts/research/tum_feasibility_probe.py` (runs only in an external sandbox).
- **Why (top reasons):** TUM's randomness lives in two interpreter-global RNGs, so forks can't share
  luck and a single extra draw shifts all later outcomes. Persistence is pickle-only over ~100
  private fields per car. Future events are pre-drawn into the state. Its shipped Monza 2019
  parameters fail to construct (two real VSCs 1.46 laps apart vs. a 1.5-lap minimum) and are
  fuel-calibrated to that race's events. It's unmaintained (Py3.8-era deps; TF/cvxpy hard imports).
  The time-discrete simulator is a self-declared proof of concept in Rust with one incomplete
  parameter file.
- **Kept from TUM as ideas only** (re-implemented, credited): per-driver accident probability,
  start performance, pit standstill distribution, overtaking time loss, FCY handling,
  degradation curve shapes.

## D-017 — M0.5 debug viewer and the visual-asset policy (2026-10-12)

- **Viewer:** `scripts/debug_viewer.py` serves one build-free page
  (`f1ar/api/static/debug_viewer.html`) from a small FastAPI app (`f1ar/api/debug_app.py`) that
  wraps one live `WorldRunner`. The page polls `/api/debug/state` (~10 Hz) and posts commands to
  `/api/debug/command`. All commands go through the runner queue and are applied at tick
  boundaries, with idempotency keys from the browser. The page never simulates. It linearly
  interpolates dot positions between polls while RUNNING and snaps to the canonical state when
  paused. This is a debug tool; the real API + React UI replace it in M3.
- **Placement:** `presentation/track_geometry.py` maps `distance_m / engine_length` onto the outline
  by arc length (fraction of a lap). The outline is 5,760 m vs the official 5,793 m, so using
  fractions means the mismatch can't push cars off the drawing. `presentation/view_model.py` is a
  pure state → JSON function (a spectator view, not a policy observation).
- **Track assets come from data, not artwork:** the outline is the winner's lap-30 path; the 11 corner
  markers and the 95° display rotation come from FastF1 `Session.get_circuit_info()`. All are derived
  from F1 timing and stay local (gitignored) like the other data.
- **Car assets:** no F1/team logos, liveries or models. Cars are dots in the **team colour from the
  official timing feed** (FastF1 `TeamColor`; a colour is data, not a mark), labelled with the 3-letter
  code. Tyres use letters plus colours (S/M/H). For M3 we can use third-party sprites only with
  recorded terms. The user-proposed **palm-tree "Formula 1 inspired 2D pixel art car pack"** (terms
  in `LEGAL_AND_LICENSES.md`) would be used with one neutral base sprite **recoloured per team
  colour at runtime**, rather than its 2021-livery-like cars, and the author is credited.
